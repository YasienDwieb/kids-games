[Flow](../concepts/flow) — the guided, scoreless play mode — is built as its
own small engine under `src/sdk/flow/`, re-exported wholesale from the SDK
barrel with `export * from './flow'` [@sdk-index], and it deliberately does
not reuse the machinery behind an ordinary game session. Where a game's
existence is decided by the [game registry](../architecture/game-registry)
(`registerGame`/`getAllGames`) and its progress lives in the per-game
`useLevels` store, flow has its own adapter registry, its own sequence
builder, and its own checkpoint store at a different storage key. The four
files that make up the engine — `adapter.ts`, `sequence.ts`, `progress.ts`,
and `useFlow.ts` — sit side by side under `src/sdk/flow/` and each owns one
stage of turning "which games opted in" into "what's rendering on screen
right now, and where do we resume if the app closes."

## Adapters: a game opts in without becoming a flow-owned thing

A `FlowAdapter` is `{ gameId, count, unitAt(i, seed): FlowUnit }`, and a
`FlowUnit` is `{ key, render(onComplete) }` [@flow-adapter]. A game opts into
flow by registering an adapter with `registerFlowAdapter()`, which stores it
in a module-level `Map<string, FlowAdapter>` — a registry structurally
identical in shape to the game registry, but a genuinely separate map with no
shared state [@flow-adapter]. `getFlowAdapter`, `getAllFlowAdapters`,
`eligibleGameIds`, and `selectedAdapters(flowGameIds)` are the read side:
`selectedAdapters(null)` returns every eligible adapter, while
`selectedAdapters([...])` filters down to the given ids, preserving
registration order and silently ignoring unknown or ineligible ids
[@flow-adapter]. `src/flow/index.ts` is the wiring file that actually
populates this registry — the flow-mode analogue of `src/games/index.ts` — and
it imports exactly six `flow.tsx` modules as side effects: `count-and-pop`,
`shape-detective`, `match-up`, `letter-land`, `numbers-land`, and
`animal-safari` [@flow-registrar]. A game that never imports a `flow.tsx`
here — `simple-pairs`, `color-mixer`, `mouse-maze`, `balloon-archer`, and
`turbo-road` — has no adapter and can never appear in a flow sequence, no
matter how complete the game itself is. `unitAt(i, seed)` is what lets a
finite, addressable slice of the game's own content become a `FlowUnit`
without the game rewriting any of its actual gameplay: the unit's `render`
function is typically the game's existing round component, wired to call
`onComplete` on success instead of updating a score.

## Building the interleaved sequence

`sequenceLength(adapters)` sums every adapter's `count`; `buildSequence(adapters)`
turns the list of adapters into a flat array of `{gameId, localIndex}` steps
by round-robining across them: game0's unit 0, game1's unit 0, game0's unit 1,
game1's unit 1, and so on, skipping any game whose `count` has been exhausted
while the others continue [@flow-sequence]. This ordering is a deliberate
product choice, not an implementation detail — a flow session mashes small
pieces of several games together in one continuous stream rather than playing
one game's contributed units to exhaustion before moving to the next. The
reasoning for building this cross-game interleave as its own subsystem rather
than as a mode bolted onto the existing per-game player is recorded in
[Flow as a separate engine](../decisions/flow-as-separate-engine).

## Resumable, seeded progress

Flow's checkpoint is a single record, `FlowProgress = {step, seed,
updatedAt}`, persisted at its own storage key distinct from any per-game
progress key — the [Storage and progress](../architecture/storage-and-progress)
page covers the shared `createStore` primitive both systems build on, and how
their keys stay separate [@flow-progress]. `seed` is what makes a resumed
session reproduce identical content: because each `FlowUnit` is generated by
`unitAt(i, seed)`, replaying the same `(index, seed)` pair after an app
restart regenerates the exact same round the child left off on, rather than a
freshly randomized one [@flow-progress]. `resolveStart(total, saved)` decides
where a session resumes — an empty journey or a saved step at or past the end
both resolve to `{done: true}`, otherwise it resumes at the saved step
[@flow-progress]. `advanceStep(total, step)` is the single-step transition:
one past the last unit flips the whole session to `done` [@flow-progress].

## `useFlow`: the state machine that ties it together

`useFlow({adapters})` is the hook `FlowPlayerScreen` calls to drive
everything above. It builds the sequence and total length once per adapter
list with `useMemo`, loads the persisted `FlowProgress` once on mount to
resolve the initial position, and exposes a `status` of `'loading'`,
`'playing'`, or `'done'` [@use-flow]. `advance()` computes the next position
with `advanceStep`, persists the furthest step reached — using the *sequence
length*, not a special sentinel, to represent "done" — and updates state;
`reset()` picks a fresh seed with `newSeed()`, persists step `0`, and starts
the sequence over [@use-flow]. The current `unit` is derived, not stored: on
every position change it looks up the responsible game's adapter via
`getFlowAdapter(seqStep.gameId)` and calls `adapter.unitAt(seqStep.localIndex,
seedRef.current)` fresh [@use-flow]. Because `unitAt` is seeded and
deterministic, this recomputation is safe — it produces the same unit the
child was already on rather than a new one.

## `FlowPlayerScreen`: a chrome of its own

`FlowPlayerScreen` is a real, registered `FlowPlayer` route, not
scaffolding. It reads `settings.flowGameIds` through `useSettings()`,
resolves `selectedAdapters(settings.flowGameIds)`, and drives `useFlow` with
that adapter list [@flow-player-screen] [@settings-store]. It renders the
current unit inside `SceneCanvas`, a shared animated backdrop, and
cross-fades between units with an `Animated.Value` timed around each
`onComplete` call, and it floats its own `BackButton` over that canvas
[@flow-player-screen]. Notably, it never touches `GameShell` or
`GamePlayerScreen` — the chrome every ordinary game session renders inside.
Flow mode (`settings.mode === 'guided'`) is a fully independent screen with
its own header-less layout, its own safe-area padding logic, and its own
"all caught up" rest state for when `status === 'done'` [@flow-player-screen].
This is the concrete shape of the parallel-engine decision: flow does not
extend `GamePlayerScreen`'s shell/bare layout modes documented in the
[game config schema](../reference/game-config-schema) reference, it bypasses
them entirely. To make an existing game flow-eligible, see
[Add a game to flow](../guides/add-a-game-to-flow).
